## 5. Termination adapter failure-path audit

**Files:** `src/drilling_intelligence/ui/lifetime.py` (979 lines, corrected), `tests/unit/test_qt_termination.py` (16), `tests/unit/test_qt_lifetime_contract.py` (22), `tests/unit/test_qt_termination_edge.py` (19 new).

**Paths audited:**

| Symbol | Question | Answer |
|---|---|---|
| `_KernelTermination.terminate` | What if pseudo handle `ACCESS_DENIED` (5)? | `already_terminating` — exit code is first terminator’s, wait via `_wait_for_termination`. |
| | What if pseudo fails with `87` then `OpenProcess` succeeds? | Retry with opened handle; on success close handle and return `accepted`. |
| | What if both fail? | `refused` with `last_error`, `attempts`. |
| | What if native raises? | Caught, `winerror` or `_last_error` or 1. |
| | What if return type not `bool`/`int`? | `1` (refused) — never read as success. |
| | Is opened handle leaked on `ACCESS_DENIED` via opened? | **Leak fixed in V8.18:** `CloseHandle` now called before every return from opened path (both accepted and `ACCESS_DENIED`); pseudo handle (`GetCurrentProcess`) never closed per MS docs. |
| `_terminate_with` | `GetLastError` unavailable/0/meaningful? | `_last_error()` returns 0 when unavailable; `_terminate_with` returns `1` when 0, so generic refusal not hidden; meaningful code preserved. |
| `_end_windows_process` | What if termination accepted but platform returned? | Defensive `_wait_for_termination` (kernel `WaitForSingleObject`) is the unreachable branch — documented as such; caller is the terminal owner that already claimed `_TERMINAL_EXIT`, so a return would be into the terminal path, not into Qt teardown. |
| `_hold_for_external_termination` | Refused forever? | Retries every 1s while holding; reports `TERMINAL_REFUSED` with error/attempts, never `os._exit` (which would be `ExitProcess`→`DLL_PROCESS_DETACH`). Documented trade-off: process waits for external terminator; exit code is terminator’s, harness records timeout. |
| `_stand_down_for_terminal_exit` | Loser waits forever? | Bounded 3s backstop, then `_end_process(4)` — never silently returns to Qt. |
| `is_fail_closed_shutdown_exit` | Only `int 4`? | Rejects `3221225477` (0xC0000005), `-1073741819`, `True`, `0`, etc. — type check `type(code) is int`. |

**Official semantics cited:**

- MS `TerminateProcess` — stops threads, does not return when terminating self, **delivers no `DLL_PROCESS_DETACH`**; `ExitProcess` does. If thread state unknown, use `TerminateProcess`. Evidence: `src/drilling_intelligence/ui/lifetime.py` docstring and ADR-61.
- MS `ExitProcess` — notifies every loaded DLL with `DLL_PROCESS_DETACH` while other threads still running (the observed fault).
- CPython `os._exit` — on Windows is CRT `_exit` → `ExitProcess` (see CPython `Modules/posixmodule.c` v3.11.9, no Windows branch).
- The historical `0xC0000005` inside `_AcceptQuit.eventFilter` (Python callback from C++) is preserved in the report; the fix is `TerminateProcess`, not a different Python finalization.

**What is covered by deterministic tests, what by stress:**

- Deterministic (injected adapter): all 12 edge cases above, plus handle-cleanup, malformed type, `GetLastError` edge, double-terminal ownership, watchdog/backstop. See §6.
- Stress (real Windows process): 25 `deadline` + 25 `deadline-synthetic` = 50 attempts, 50/50 exit 4, 0 native faults — see §7.
