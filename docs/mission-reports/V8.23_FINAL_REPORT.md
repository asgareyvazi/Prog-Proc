## 3. P1 (V8.23) — Lifetime Fail-Closed Hardening (Exit-4, no os._exit fallback)

**Threat:** `tests/unit/test_ui_coverage_boost_v22.py::test_lifetime_application_shutdown_mocked` (and potential future tests) called `lifetime.application_shutdown(MagicMock(), 0)` with only `patch.object(lifetime, "_wait_for_termination", ...)` + `patch.object(lifetime, "_end_windows_process")`, leaving `fail_closed_shutdown` → `_end_process(SHUTDOWN_INCOMPLETE_EXIT)` → `os._exit(4)` on POSIX reachable in the **main pytest runner**. The test asserted `assert result in (0, {"ok": True}, 7) or isinstance(result, (int, dict))` — a vacuous `assert True` — and did not patch `_TERMINATION`, `_TERMINAL_EXIT`, `os._exit`, or `fail_closed_shutdown`. On Linux headless (where `PySide6` import inside `finish_qt_application` raises `ImportError` → `except Exception: fail_closed_shutdown(ReleaseResult(0, ("release-exception",)))` → `os._exit(4)`), the main runner is killed with exit 4.

## 5. Win32 fail-closed semantics (preserved, wording additive)

`src/drilling_intelligence/ui/lifetime.py` (`_WAIT_OBJECT_0=0`, `_WAIT_TIMEOUT=258`, `_WAIT_FAILED=0xFFFFFFFF`, `PRODUCTION_SHUTDOWN_WAIT_MS=120_000`, `_TERMINATION_WAIT_S=2.0`) unchanged except for V8.22 `WorkerError` import refactor (no effect on wait). Contract wording remains additive, not erasing observed crash:

> The access violation (`0xC0000005` `STATUS_ACCESS_VIOLATION`, reported as `3221225477` decimal and `−1073741819` signed) occurred when the process was ended through `ExitProcess` (`os._exit` → `C runtime _exit`/`_Exit` → `ExitProcess`) which delivers `DLL_PROCESS_DETACH` to every loaded library while the other threads are still running. A library teardown (Qt/PySide6/shiboken) ran against a live thread inside a Python callback invoked from C++ (Qt event filter `QEvent::Quit` → Python `eventFilter`), faulting the thread that was inside the filter when the process died, while the stack dump showed another thread. Microsoft guidance is the same: if thread states are unknown, call `TerminateProcess` rather than `ExitProcess`. `TerminateProcess` stops threads without notifying libraries (`DLL_PROCESS_DETACH` not delivered), so it does not run native static destruction or `DLL_PROCESS_DETACH` handlers. The fix is `TerminateProcess` via `_KernelTermination`/`_TERMINATION.terminate(code)` + `_wait_for_termination` (kernel wait `WaitForSingleObject`) + `_hold_for_external_termination` on refusal, never `os._exit`/`ExitProcess` on Windows, with single-terminal-owner (`_TerminalExit`) and bounded shutdown (`_ShutdownDeadline`). `is_fail_closed_shutdown_exit` accepts only `int 4` (rejects `3221225477`, `-1073741819`, `True` (bool is not int), `0`, `1`, `5`).

Distinguishes: interpreter finalization (skipped by `os._exit`/`TerminateProcess`), CRT `_exit`/`_Exit` (calls `ExitProcess` on Windows), `ExitProcess` (notifies DLLs), `TerminateProcess` (does not), `DLL_PROCESS_DETACH` (per-DLL entry point), native static destruction (not run by `TerminateProcess`), Qt/PySide6/shiboken teardown (runs on `DLL_PROCESS_DETACH`), fault on thread inside Python callback (the faulting thread), stack dump showing another thread (the dump).

Preserved: `test_kernel_wait_returns_wait_failed_on_exception` still injects fake `WinDLL` with `raising=False`, asserts `WAIT_FAILED`; `test_a_refused_termination_is_not_turned_into_a_success` etc. still verify `hold` not `exit` on Windows.
