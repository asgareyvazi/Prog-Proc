## 2. P1 and P2 — the shutdown, and the label on it

The V8.16 report said the native access violation came from "the Python
interpreter finalizer". That label is wrong, and the correction is ADR-61:

* CPython's `os._exit` is the CRT `_exit`, which on Windows calls
  `ExitProcess`. There is no Python interpreter finalization on that path.
* `ExitProcess` notifies every loaded DLL with `DLL_PROCESS_DETACH` while the
  other threads are still running — here, the GUI thread inside a Python
  callback (`_AcceptQuit.eventFilter`), with the `QApplication`, the
  PySide6/shiboken bindings and Qt's own static destructors still alive.
* `TerminateProcess` notifies no library. That is the mechanism the fix uses.

The observation is not withdrawn: at least ten faults in fifty attempts at
`eab9323`, inside the DLL-detach teardown. Only the name of the mechanism was
corrected, additively, in ADR-61, in `docs/WINDOWS_TESTING.md` and in the two
end-to-end reports.

What the phase left behind:

| Artefact | What it does |
| --- | --- |
| `src/drilling_intelligence/ui/lifetime.py` | One termination kernel with an **injectable** adapter. Windows refuses to use `ExitProcess`; a refusal is reported loudly and is never a success and never an `os._exit` fallback. POSIX keeps `os._exit(code)`. |
| `tests/unit/test_qt_termination.py` | 16 tests: success, retryable refusal, permanent refusal, native exception, wrong native return type, error-code preservation, deadline expiry, watchdog delegation — with a fake adapter, so no real process is killed in the pytest process. |
| `tools/qt_shutdown_stress.py` | Every attempt recorded: mode, ordinal, raw exit code in decimal and hex, duration, phase markers, faulting frames, terminal-owner markers, failure reason, runtime versions, log path. A JSON summary with disjoint, exhaustive counts. `--gate` fails the step on a fault. |
| `tests/unit/test_qt_shutdown_stress.py` | 20 tests over the record format, the counts and the gate. |

`is_fail_closed_shutdown_exit` accepts the integer `4` and nothing else. It
rejects `3221225477`, `-1073741819`, `True` and `0`, and that is tested: an
access violation can never be relabelled as a clean shutdown.

## 3. P3 — the flaky workbench test

Three phases of evidence before a single line was changed:

1. 25 isolated runs of the failing node in fresh processes: **25/25 green**.
   The flake was not in the node.
2. 16 full-suite runs: green. The flake was not a load-dependent race.
3. The session-scoped `qt_app` fixture was the common factor: six tests closed
   their window but never released the top-level widget, and the session-end
   teardown then destroyed a `QApplication` that still owned live widgets —
   a native abort, on Windows.

The fix is `release_top_level_widgets(qt_app)` in the six tests that build a
window, plus a fixture assertion that no top-level widget survives a test. No
sleep, no retry, no weakened assertion. A 25-attempt probe after the fix was
**25/25 green** (`/tmp/ui_flaky_runs3.txt`, `PROBE_COMPLETE`). ADR-62 records
the cause; ADR-56 and ADR-60 carry dated corrections.

## 7. P7 — the pins

Five findings, each one a defect the review was supposed to find:

1. **The auditor floated.** Both workflows installed `pip-audit>=2.9,<3`
   into the product's environment. Two audits of one commit were not
   comparable, and installing the tool could move a version the product is
   tested with. `constraints/audit.txt` now pins it (`pip-audit==2.10.1`) and
   the workflow builds it an environment of its own.
2. **The drift check was date-dependent.** `tools/constraints.py --check`
   rendered the expected file with *today's* date, so on 2026-10-25 all five
   sets failed while every pin was current. The comparison now feeds the
   file's own date back in, and the check runs in CI.
3. **The auditor's environment was inside the checkout.** The Windows job
   failed its own "working tree was not rewritten" check at `14e24a5`
   because the audit step had created `.audit-venv` in the tree it was
   inspecting. It is built in `$RUNNER_TEMP` now.
4. **PowerShell does not stop on a native failure.** The Windows audit step
   would have gone green on an audit that never ran. Every native call is
   checked now.
5. **The pins had drifted.** All four product sets were renewed by the
   recorded command: SQLAlchemy 2.1.6, alembic 1.20.1, certifi 2026.10.23,
   coverage 7.17.0, ruff 0.17.2, setuptools 84.2.1; PySide6 6.12.0 unchanged.

Every action in both workflows is pinned to a full commit SHA, and the policy
test records the upstream tag each pin came from (checkout `v7.0.1`,
setup-python `v7.1.0`, upload-artifact `v7.0.2`).

With the date fixed, all five sets report `is up to date` on 2026-10-25, and
the audit reports `clean`, 0 findings, against the pinned runtime and UI sets.

## 8. P8 — exceptions, and a real secret in a real log

The review read all 86 broad handlers in `src/` and `tools/` with `ast`:
**21 suppress, 53 report, 12 re-raise**, with 0 bare `except` and 0
`except BaseException`. Every suppression carries a written reason —
`tools/exception_review.py --check` fails on an undocumented one — and the
six handlers that carried a bare marker now say what they are for.

The review found a security defect. `core/logging.py` masked a value only
when the *value* looked like a token, and the `sk-` pattern captured the
secret and re-emitted it inside the replacement, so a secret of that shape
was written to the log in full; a field whose **name** said it was a secret
was not masked at all when its value was a plain string. The mask is now by
name first and by shape second, and the token pattern has no capture group.
`api_key: "sk-…"` is written as `api_key: "***REDACTED***"`.
