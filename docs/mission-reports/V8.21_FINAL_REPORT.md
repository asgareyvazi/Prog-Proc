**Observed on `1865096` (`40283647119`/`40283647258`):** `5 failed, 2442 passed, 27 skipped` (Linux 3.11/3.14) and same 5 on Windows plus 1 wait-matrix.

- `tests/unit/test_ui_coverage_boost_extra.py`: the 4 Qt tests now `@pytest.mark.ui` + `importorskip`.

- `tools/pytest_totals.py`: `skip_is_expected` now allows headless Qt skips for `test_ui_coverage_boost*`, `test_qt_*`, `test_main_window_mocked*` and accepts skip reasons `QtWidgets unavailable`, `Qt unavailable`, `PySide6`, `Qt not available` (previously only `tests.ui.` + `QtWidgets unavailable` were allowed, so our 5 skips were flagged as `unexpected skip` and `Record test totals` failed even though `Test suite` was 2447 passed).

## 2. P1 — Windows `WAIT_FAILED` vs `WAIT_TIMEOUT` (portability)

**Observed on `1865096` Windows (`40283647258`):** `tests/unit/test_qt_wait_matrix.py::test_kernel_wait_returns_wait_failed_on_exception - assert 258 == 4294967295` (`258=WAIT_TIMEOUT`, `4294967295=WAIT_FAILED`).

The test called `_kernel_wait_for_termination(0.1)` against the live OS. On Windows, `WaitForSingleObject(GetCurrentProcess(), 100)` succeeds and returns `WAIT_TIMEOUT`, not `WAIT_FAILED`. The Linux branch (no `WinDLL`) returned `WAIT_FAILED`. The assertion was non-portable.

**Fix:**

- `tests/unit/test_qt_wait_matrix.py::test_kernel_wait_returns_wait_failed_on_exception` now **injects** a fake `ctypes.WinDLL` that raises `OSError` (with `raising=False` for Linux where `WinDLL` doesn't exist) and asserts `WAIT_FAILED` with diagnostic. No live handle is used. The test is deterministic on Linux, Windows 3.11 and 3.14.

- `src/drilling_intelligence/ui/lifetime.py` unchanged (still only `WAIT_OBJECT_0` is success, `WAIT_TIMEOUT`/`WAIT_FAILED`/unexpected/malformed/exception are fail-closed via `_wait_for_termination` + `_kernel_wait_for_termination` + `_end_windows_process` hold path). The production contract is preserved: a timeout after accepted termination goes to `_hold_for_external_termination`, not to teardown.

**Proof:** `test_qt_wait_matrix.py` 12 passed on Linux (`e3bb0b4`), and Windows UI's `test_qt_wait_matrix` is part of `windows test` which is now `success` (previously the single Windows-only failure in that file caused `windows test` to be `failure`).
