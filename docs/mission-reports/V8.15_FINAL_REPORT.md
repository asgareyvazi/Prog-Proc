## 4. Investigation timeline

1. The test `test_synthetic_deadline_is_supplementary_not_the_qthread_proof` starts `tests/ui/qt_shutdown_child.py` in a subprocess. The child builds a real `QApplication` and `MainWindow`, attaches a `Busy` stand-in that reports running for 30 seconds, enters `exec()`, quits, prints `SYNTHETIC_DEADLINE`, and calls `application_shutdown(..., deadline_ms=400)`.
2. The intended proof is supplementary. It is not a `QThread` integration proof. The production deadline test owns a real `QThread`.
3. While the stand-in is running, `owned_workers_running()` is true, so the coordinator does not call `close()`. The expected terminal is process exit 4 from `fail_closed_shutdown` or the deadline monitor. The child must not return.
4. On `4029ece`, Windows UI job failed this test. The annotation showed a `PYTHONFAULTHANDLER` stack whose newest Python frame was `finish_qt_application`. The exact child code was outside the 500-character detail window. That run is not a pass.
5. `3853862` made the Windows monitor call `TerminateProcess` with code 4 before `os._exit`. It does not call Qt, delete a widget, or `QThread.terminate` a worker. `13ab9bd` formatted the test. Its Windows UI job passed 22/22. That pass does not prove the fault was gone.
6. On `69c4bd4`, a docs-only descendant of `13ab9bd`, the same test failed again. This session re-read check-run `117728065498`. `head_sha` is `69c4bd4ee98b518705ff59f0d444e3f0cd3aee9f`. Conclusion is `failure`. The annotation is `exit 3221225477` (`0xC0000005`). The stack order is faulthandler order, newest Python frame first: `finish_qt_application` line 405, which is `return _coordinate(...)` on the fail-closed path, then `application_shutdown`, then `deadline_synthetic`. Stdout had reached `SYNTHETIC_DEADLINE`. The workflow run https://github.com/asgareyvazi/Prog-Proc/actions/runs/39145391626 has run conclusion `cancelled` because a later push cancelled the still-running test jobs. The UI job itself failed before that cancellation. Cancellation of the run is not a pass of the job.
7. `2e1f5e6` stopped `processEvents` when a pass only waits for a live worker. `ef6a727` recorded that CI. Both of those Windows UI jobs passed 22/22. Two passes do not prove the fault cannot recur.

## 6. Root-cause conclusion

**Unproven.** The probable class is a native fault on the GUI thread inside `_coordinate` during the 400 ms wait, after `exec()` had returned and while the `Busy` stand-in was still running.

What the evidence supports:

- The faulting Python frame is the main thread inside `finish_qt_application` / `_coordinate`, not the monitor thread inside `_terminal_exit`.
- The child had already printed `SYNTHETIC_DEADLINE`, so the crash is in `application_shutdown`, not in `exec()`.
- `3221225477` is `0xC0000005`, an access violation, not exit 4. The parent assertion did not mask it.
- `TerminateProcess` was already present on `69c4bd4` and did not prevent the fault.
- While the worker is running, the coordinator still calls `QApplication.topLevelWidgets()`, `shiboken6.isValid`, and `QThread.msleep`. Before `2e1f5e6` it also called `processEvents`.
- C frames were truncated from the annotation. The zip was not downloaded. The crashing native call is not identified.

What was not established: use-after-free of a specific `QObject`, a cross-thread Qt call from the monitor, a bad `TerminateProcess` interaction, or a deterministic Windows reproduction.

No production shutdown sequence was rewritten on that unproven cause.

## 7. Regression protection and its limits

- The deadline tests now call `is_fail_closed_shutdown_exit`. Only the integer 4 is accepted. `3221225477`, `-1073741819`, `0`, `1`, `134`, and `True` are rejected by a unit test that does not need Qt.
- The parent still captures the raw `subprocess` return code and prints it in the assertion detail. That is how `3221225477` was observed.
- The Windows UI job still runs `tests/ui` once. It has no `continue-on-error` and no retry. `PYTHONFAULTHANDLER=1` remains set.
- A 15-repeat of this child was not added to required CI. The existing assertion already fails on the access violation. Repeating an unproven fault 15 times would make the required UI job intermittent without identifying the native call. Estimated added time, from the 400 ms deadline plus process startup, is on the order of half a minute, which would have been proportionate if the loop were a stable detector. It is not stable until the fault can be reproduced on demand.
- Limitation: one execution can miss the fault, as `13ab9bd` and `ef6a727` did. Absence of a failure in those jobs is not a fix.
