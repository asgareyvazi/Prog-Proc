# Engineering Program and Procedure Capability Plan

**Authority:** current engineering capability inventory and ordered roadmap for Prog-Proc. Historical reports remain historical evidence; this plan does not retroactively reclassify them. **Product state remains local-first, single-user, Pre-Alpha.** This plan is source-grounded at repository tip `7b045178df7452785e3485e5a81443062b639763`; the current mission changes in the working tree have not yet been committed or CI-qualified.

## 1. Existing engineering capabilities from the project's beginning

Status vocabulary: **usable** = public workflow and persistence exist; **service-only** = repository/service has behavior but no ordinary user mutation surface; **extract-only** = source parsing/promotion boundary only; **read-only** = projection; **partial** = a narrower subset exists; **owner-gated** = no authority to decide the engineering rule; **not qualified** = no acceptance evidence. UI/CLI entries describe public user paths, not merely Python APIs.

### Capability inventory

1. **Well, project, field, and section hierarchy** — scope/identity records and planned-vs-actual separated values. Sources: `database/models.py` (`Project`, `Field`, `Well`, `WellSection`), `wells/repository.py`, `wells/workspace.py`; CLI `drillintel wells`; UI well selector, Overview, Sections. Tests: `tests/unit/test_cli.py`, `tests/integration/test_well_section_contract.py`, `test_section_population.py`, `test_plan_actual_forensics.py`. Workflow: register a well, inspect its sections, and record actuals through the operational/workbench flows. **Usable for registry/operational data; not a trajectory or full well-design editor.**
2. **Drilling Program identity/revisions/status/scope** — `DrillingProgram` has identity, scope, author/reviewer/approver strings, schedule dates, provenance, lifecycle and supersession. Sources: `database/models.py`, `engineering/repository.py`; CLI: no Program authoring group at the baseline; UI: Review Workbench is read-only for Program records. Tests: `tests/integration/test_engineering_lessons.py`, `test_program_promotion.py`, `test_plan_actual_forensics.py`, `test_domain_review.py`. **Service-only** before this mission slice. Approval attribution is not authentication; repository approval itself does not prove engineering adequacy.
3. **Program targets and plan-versus-actual** — `ProgramTarget` stores named planned section targets, selected hole/casing/depth/duration/mud/NPT/cost values, explicit units, provenance and attributes; `EngineeringRepository.plan_actual_summary` compares supported metrics while preserving absent-side and unit mismatch semantics. Sources: `database/models.py`, `engineering/repository.py`, `operations/program.py`; no baseline Program mutation CLI/UI. Tests: `test_well_section_contract.py`, `test_section_population.py`, `test_program_promotion.py`, `test_plan_actual_forensics.py`, `test_engineering_lessons.py`. **Service plus extraction/read projection; not a complete Program document.**
4. **Program document extraction/promotion** — typed extraction fields with quality, units, provenance/locators; only valid unambiguous supported fields become targets, otherwise skipped with reason. Sources: `operations/program.py`, `operations/promote.py`, `extraction/{pdf_text,fields,normalized}.py`; public user path is ingest/intake plus promotion, not a structured editor. Tests: `tests/integration/test_program_promotion.py`, extractor suites. **Extract-only/narrow promotion; never auto-approval.**
5. **Procedure records/revisions/lifecycle/references** — `ProcedureRecord` stores title/type/scope/description/source/revision/approval attribution and knowledge relationships to Program, standard/document version, lessons, calculations, risks, etc. Sources: `database/models.py`, `engineering/repository.py`; no baseline public mutation CLI/UI; read-only domain review only. ## 2. Current implementation state and public workflow gaps

- Before the current worktree slice, Programs and Procedures had schema/repository lifecycle, but no mutation CLI and no authoring UI. A model/repository method is not an end-user authoring product.
- This worktree slice introduces a strict bounded JSON CLI boundary and domain service, not a writable Qt experience. It has no templates, export, full review-comment interface, delete controls, or source-document-to-draft mapper yet.
- Existing `approve_program` / `approve_procedure` repository APIs remain legacy service methods. The new public workflow requires submission, a separately attributed review, a reasoned decision, and a structural checklist; declared actor strings are **not authentication** and do not prove independent identity.
- Program structural validation does not assess whether engineering design values are complete/safe. Procedure structural validation does not assess operating safety. Readiness only reports the literal checklist it implements.

## 3. Implemented calculations and existing engineering records

Only `npt.hours_rollup` V1 executes. Generic calculation rows are audit/storage. Program targets compare supported planned values to actual section/DDR/NPT values with missingness and unit-identity surfaced. Risk scores, trajectory, hydraulics, casing, cement volumes, torque/drag, cost/AFE/FX and pressure-window methods do not execute.

Existing record families: hierarchy/sections; Programs/targets; Procedures; DDR/activity; operations/events/NPT/problems; mud; BHA/components/bits; surveys; casing/cement; well control/HSE; risks/costs; lessons/practices/recommendations; calculations/inputs; documents/versions/extractions; knowledge/evidence/conflicts/audit; reports/comparisons/patterns.

## 4. Engineering gaps and planned modules

Priority 1 **Program Builder** — editable structured cover, design basis, prognosis, hole/casing/mud/bit/BHA/survey/cement/well-control/risk/time-cost/logistics/references, target editor, completeness, exact revision and controlled exports. **Ready for iterative implementation** of authoring surface; engineering defaults require source or owner-approved template, and technical values need qualified inputs.

Priority 2 **Procedure Builder** — full control, scope, roles, preconditions, equipment, safety, ordered steps, hold points, acceptance, contingency, completion/records, revision review and publishing. Structured step storage and CLI exist only in this worktree; UI, templates, export, richer review and operational test remain. **Ready for implementation** with safety wording always sourced and independently reviewed.

Priority 3 **Program/Procedure linkage** — **partially implemented (migration `0028`, headless CLI)**: a current DRAFT Procedure links to one exact Program revision (`procedures link-program` / `program-link`, `programs linked-procedures`); cross-well links are refused and a newer current Program revision marks the link `STALE` with `review_needed`. Still missing: section/target-level links, impact review workflow, operational/DDR/NPT evidence linkage.

Priority 4 **Engineering calculation workspace** — method registry, approved versioned calculation contracts and traceable inputs/results. Only NPT roll-up executes. **Requires owner decision and approved engineering standards** per method; directional/trajectory specifically remains disabled pending the packet in section 7.

Priority 5 **Technical review/approval** — completeness and consistency, role attribution, review history, decision reasons and exact-content revision control. Current slice supplies structural checks and a technical-review audit note; no authentication/authorization. **Requires product owner policy** for authority, segregation, approval states, and access model.

Priority 6 **Professional documents** — controlled DOCX/PDF, draft watermark/status, citations, revision/approval history, atomic no-clobber export. Existing report HTML is not a Program/Procedure document generator. **Requires design** and DOCX/PDF fixtures; no approval badge until exact revision is approved.

Priority 7 **Engineering intelligence** — revision-aware plan/actual across Program/Procedure/DDR/NPT, stale links, risks/lessons, historical comparison. Existing reports provide a narrower projection. **Requires technical design and field data validation**; no inferred recommendations.

## 7. Directional calculation approval packet

Before any trajectory method is enabled, owner must record: (1) algorithm and controlled reference/version; (2) MD/TVD/inclination/azimuth conventions and units; (3) north reference, coordinate system and datum; (4) station spacing, invalid, repeated and zero-length behavior; (5) dogleg limits and refusal conditions; (6) uncertainty/toolface scope; (7) independently checked reference vectors, tolerances, edge cases and reviewer. Until then `SurveyRun`/`SurveyStation` are source records only and no trajectory/TVD/displacement/DLS is calculated.

## 8. Release sequence

1. **MVP-1 (current slice):** SQLite migration `0027`, revision-owned structured Program sections and Procedure steps, conservative service validation, strict CLI create/edit/reorder/review/revision/compare, focused integration tests.

4. **MVP-4:** governed, content-only templates and realistic synthetic golden Program/Procedure documents; extraction creates DRAFT proposals only.
5. **MVP-5:** controlled DOCX/PDF/JSON export, review packet, document diff and audit/provenance validation.
6. **MVP-6:** calculation registry and one owner-approved method at a time; preserve all current refusal boundaries.
7. **Qualification:** exact-SHA Linux/Windows CI, real user/operator acceptance where needed; product remains Pre-Alpha until owner-defined release criteria are met.
